Pull requests: review gates for safer DevOps delivery

A pull request is more than a request to merge code. In DevOps, it is a control point where teams review infrastructure, pipelines, Kubernetes manifests, Dockerfiles, runbooks, and security-sensitive changes before they reach shared branches or production workflows.

Visual model

What a pull request protects

The pull request sits between a branch and the main branch. It creates a review space where automation and humans can check the change before it becomes part of the trusted delivery path.

branchfeature/change

Work happens away from main.

checksCI + scans

Tests, linting, builds, plans, and scans run.

reviewapproval

Team members check risk, quality, and intent.

mainmerge

Only ready changes enter the shared branch.

Why PRs matter

They create controlled visibility

Pull requests show exactly what is changing before the change lands. For DevOps work, this is essential because a small file update can affect networking, permissions, deployments, costs, monitoring, or service availability.

DevOps value

They turn delivery into a team sport

A good PR connects code, context, tests, risk, reviewers, approvals, and deployment evidence. It helps teams avoid silent changes and makes production delivery easier to audit.

Hands-on lab

Create a pull request for a pipeline documentation change

This lab uses Git commands to create a branch and push it. After pushing, you would open the pull request in GitHub, GitLab, Azure Repos, or Bitbucket. 

# Start from main
git switch main
git pull origin main

# Create a clear branch
git switch -c docs/add-pr-checklist

# Add a useful checklist
mkdir -p docs
cat > docs/pull-request-checklist.md <<'EOF'
# Pull Request Checklist

- What changed?
- Why was the change needed?
- How was it tested?
- What is the risk?
- Is rollback possible?
- Are secrets or permissions affected?
EOF

# Review, commit, and push
git diff
git add docs/pull-request-checklist.md
git commit -m "Add pull request checklist"
git push -u origin docs/add-pr-checklist

Good PR content

What a strong pull request should include

What changed

Summarise the exact file, infrastructure, pipeline, or service change.

Why it changed

Explain the problem, requirement, incident, feature, or operational need.

How it was tested

Include commands, screenshots, CI runs, Terraform plans, or deployment checks.

Risk

Call out networking, permissions, production impact, downtime, data, or cost risk.

Rollback

Explain how to revert, redeploy, restore config, or recover safely.

Reviewers

Ask the right people to review: platform, security, app owner, data, or operations.

DevOps examples

Pull requests are not only for application code

Terraform

Review a plan before infrastructure is created, changed, or destroyed.

Jenkinsfile

Check pipeline stages before a bad update breaks delivery for the team.

GitHub Actions

Validate workflow syntax, permissions, secrets use, and deployment gates.

Kubernetes

Review image tags, probes, resource limits, ingress, secrets, and namespaces.

Dockerfile

Check base images, exposed ports, package installs, user context, and vulnerability scans.

Runbooks

Improve incident steps before the team needs them under pressure.

Automation gates

Useful checks before merge

lint

Check formatting, YAML, shell scripts, Dockerfiles, or Terraform style.

test

Run unit, integration, smoke, or contract tests depending on the change.

scan

Run dependency, image, secret, IaC, and container vulnerability checks.

plan

For Terraform, review what will be added, changed, or destroyed.

build

Confirm the artifact, container image, or package can be created successfully.

approve

Require human approval for risky or production-impacting changes.

Template

A practical pull request template

A pull request template helps every change carry the same minimum information. This is useful for teams that manage infrastructure, security, deployments, and production support. 

## Summary
Explain the change in 2-3 sentences.

## Why
Describe the reason for the change.

## Testing
- [ ] Unit tests passed
- [ ] CI pipeline passed
- [ ] Terraform plan reviewed
- [ ] Smoke test completed

## Risk
Describe production, security, data, or networking impact.

## Rollback
Explain how to revert or recover if the change fails.

## Reviewer notes
Mention anything reviewers should focus on.

Review mindset

How to review a DevOps pull request

Read the intent

Does the PR explain why this change exists?

Check the diff

Do the changed files match the stated purpose?

Look for blast radius

Could this affect production, security, networking, data, or users?

Confirm tests

Are checks meaningful, or did the author only say it works?

Question secrets

Are credentials, tokens, private keys, or sensitive values exposed?

Think rollback

If this fails, can the team recover quickly?

Troubleshooting

Common pull request problems

Too large

Split unrelated work into smaller PRs so reviewers can understand the change.

No context

Add a clear summary, reason, test evidence, risk, and rollback note.

Checks failing

Read the CI logs, reproduce locally, fix the branch, and push again.

Review ignored

Reply to comments, update the branch, or explain why a suggestion was not used.

Conflicts

Update the branch from main, resolve conflicts, test, and push the resolution.

Secrets exposed

Remove the secret, rotate it, review history, and improve secret scanning.
