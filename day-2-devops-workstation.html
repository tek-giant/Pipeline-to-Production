Day 2 of 100

Setting up a DevOps workstation that is ready for real work

A DevOps workstation should make everyday engineering faster, safer, and more repeatable. Before pipelines, containers, cloud platforms, and Kubernetes, the local environment must be clean, documented, and easy to rebuild.

Build the setup Back to roadmap
Today's focus Workstation readiness

Editor, terminal, Git, SSH, Docker, cloud CLI, documentation, and secure working habits.

Why it matters

Your workstation is the first delivery environment

The tools used locally shape how smoothly code is written, tested, scanned, packaged, pushed, and deployed. A messy setup creates repeated friction. A reliable setup gives every future DevOps task a stable base.

Professional habit

Make the setup repeatable

A good engineer does not only install tools. They document versions, commands, folder structure, and setup decisions so the environment can be recreated on another laptop or explained to a team.

Security mindset

Protect access from day one

DevOps work often touches repositories, servers, cloud accounts, credentials, and production-like systems. Use safe authentication, avoid committing secrets, and keep sensitive values out of notes and screenshots.

Core setup

The workstation toolkit

The goal is not to install every tool in the DevOps world on Day 2. The goal is to create a dependable base that can support Linux practice, Git workflows, scripting, containers, cloud work, CI/CD labs, and future Kubernetes projects.

01 Editor

Use VS Code with extensions for YAML, Docker, Markdown, Git, Terraform, and Kubernetes.

02 Terminal

Use Windows Terminal, PowerShell, Git Bash, or WSL so command-line work feels natural.

03 Git

Configure name, email, default branch, credential helper, and common aliases.

04 SSH

Create SSH keys for secure GitHub and server access without exposing passwords.

05 Docker

Install Docker Desktop or a container runtime to prepare for image and container labs.

06 Cloud CLI

Install AWS CLI and learn how profiles, regions, output formats, and credentials work.

07 Package manager

Use winget, Chocolatey, Homebrew, apt, or another package manager to simplify installs.

08 Documentation

Use Markdown notes so every command, error, fix, and decision becomes reusable knowledge.

09 Secrets hygiene

Use environment variables, `.gitignore`, and a password manager. Never commit credentials.

10 Browser setup

Keep quick access to GitHub, AWS docs, Kubernetes docs, Docker docs, and Jenkins docs.

Recommended structure

Create one clean DevOps workspace folder

Put learning notes, scripts, small projects, architecture diagrams, and lab files in a clear folder structure. This makes the work easier to find, easier to push to GitHub, and easier to show in a portfolio.

Hands-on task

Build the Day 2 folder and commit it

The practical task is to create the folder, initialise Git, add a Day 2 note, and commit the structure. This turns the lesson into real evidence that can be shown publicly.

What to document

Write the note like an engineer

List every installed tool and the reason it is needed.

Record version checks such as `git --version`, `docker --version`, and `aws --version`.

Write the folder structure and explain what each folder is for.

Add Git configuration commands for name, email, default branch, and status checks.

Explain where secrets should live and where they should never live.

Capture any setup issue and the exact command or setting that fixed it.

Verification

Prove the workstation is ready

A setup is only useful when it can be verified. Run quick checks before moving on to Day 3 so future Linux, Git, automation, container, and cloud exercises do not fail because of missing local tools.

git terminal editor ssh docker aws cli notes commit

Security habits

Start clean before touching cloud accounts

Never commit secrets

Use `.gitignore` for local files, avoid pasting credentials into Markdown, and review changes before commits.

Use SSH properly

Prefer SSH keys for GitHub and server access, and protect private keys like production credentials.

Separate profiles

Use named cloud profiles so personal labs, demos, and work accounts do not get mixed together.

Keep tools updated

Update the editor, Git, Docker, and CLIs regularly so security fixes and compatibility improvements are applied.

Check before sharing

Before posting screenshots or repositories, check for access keys, account IDs, private URLs, and tokens.

Portfolio evidence

What readers should see after Day 2

By the end of Day 2, a reader should see a clean GitHub repository, a useful README, a Day 2 setup note, sensible folder names, and a small commit history. This proves organisation, documentation discipline, and readiness for hands-on DevOps work.

Can another person understand the setup from the README?

Can the workstation support the next Linux and Git lessons?
