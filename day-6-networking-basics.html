Day 6 of 100

Networking basics: how systems actually reach each other

Many DevOps problems are communication problems. The application may be running, but DNS may fail, a port may be closed, a firewall may block traffic, TLS may be misconfigured, or a load balancer may have no healthy targets. Day 6 gives readers a practical way to reason about network flow.

Mindset

Networking explains reachability

A service can be healthy locally but unreachable to users. DevOps engineers need to check the path from source to destination: name resolution, route, firewall, port, protocol, load balancer, and backend health.

Outcome

Move from guessing to structured checks

Instead of saying "the app is down", a stronger engineer asks: can the client resolve the name, reach the host, connect to the port, complete TLS, and receive a healthy response?

Core concepts

The network terms every DevOps beginner should know

These concepts appear in cloud platforms, Kubernetes Services, ingress controllers, CI/CD runners, firewalls, databases, APIs, load balancers, and production incident calls.

IP addressMachine address

Identifies a host or interface on a network.

DNSName resolution

Turns names like `api.example.com` into IP addresses.

PortService doorway

Allows applications to listen for specific types of traffic.

TCPReliable connection

Used by SSH, HTTP, HTTPS, and many databases.

UDPConnectionless traffic

Often used for DNS, streaming, and low-latency traffic.

HTTPWeb protocol

Moves web requests and responses between clients and servers.

HTTPSSecure web protocol

HTTP protected with TLS encryption.

TLSEncryption layer

Protects traffic and helps verify server identity.

Troubleshooting flow

Use this order when something is unreachable

01Resolve

Does DNS return the expected address?

02Route

Can traffic leave the source and reach the destination network?

03Allow

Do firewalls, security groups, or NACLs allow the traffic?

04Listen

Is the target process listening on the expected port?

05Respond

Does the service return a healthy application response?

Real DevOps scenarios

Where networking knowledge saves time

Cloud access

EC2 is healthy but unreachable

The instance may be running, but a route table, public IP, Security Group, NACL, subnet, or SSH service issue can still block access.

Kubernetes

Pod runs but traffic fails

A Pod may be healthy while the Service selector, target port, ingress rule, readiness probe, or backend endpoint is wrong.

Databases

Application cannot connect

Database failures often come from DNS, credentials, firewall rules, subnet routes, TLS settings, or the database not listening on the expected port.

Command guide

The commands to practise today

ping

Tests basic reachability, when ICMP is allowed.

curl

Tests HTTP and HTTPS responses from APIs and web services.

nc -vz

Checks whether a TCP port is reachable.

ss -tulnp

Shows listening ports and related processes.

nslookup

Checks DNS resolution for a domain name.

dig

Gives deeper DNS query information.

traceroute

Shows the route packets take toward a destination.

ip route

Shows how the machine chooses network paths.

Safe habits

Do not troubleshoot networking randomly

Test from the same source that is failing, not only from your laptop.

Check DNS before blaming the application.

Confirm the target service is listening before changing firewall rules.

Check cloud Security Groups, NACLs, and routes together.

Use HTTPS checks to confirm TLS and application response.

Write down the exact command, result, and next decision.
