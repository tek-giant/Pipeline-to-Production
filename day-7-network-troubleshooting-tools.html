Day 7 of 100

Network troubleshooting tools: prove where the failure is

A strong DevOps engineer does not stop at saying "the application is not working". They collect evidence. Day 7 focuses on the tools that help prove whether the issue is DNS, routing, firewall rules, listening ports, TLS, HTTP response, load balancer health, or the application itself.

Start the tool lab Back to roadmap
Today's focus Evidence-based debugging

`ping`, `curl`, `nslookup`, `dig`, `ss`, `nc`, `traceroute`, `telnet`, status codes, and command output.

DNS Does the name resolve?

`nslookup` and `dig` confirm whether the domain points to an address.

PORT Can the port be reached?

`nc`, `telnet`, and `ss` help prove whether a service is listening or reachable.

HTTP What does the app return?

`curl` reveals headers, status codes, redirects, TLS behaviour, and API responses.

PATH Where does traffic travel?

`traceroute` helps show the route between source and destination.

Mindset

Troubleshooting starts with narrowing the fault

Network tools help separate assumptions from facts. A failed request might be caused by DNS, an incorrect port, a closed firewall rule, an unhealthy backend, a TLS problem, or an application error. Each tool removes one layer of uncertainty.

Outcome

Say what is proven, not just what feels broken

A stronger answer is: DNS resolves correctly, port 443 is reachable, TLS completes, but the API returns 500. That tells the team to move past network reachability and investigate application logs.

Troubleshooting toolkit

The tools every DevOps beginner should practise

These tools appear constantly when debugging Linux servers, EC2 access, load balancers, Kubernetes Services, ingress errors, database reachability, CI/CD runner issues, and API failures.

pingBasic reachability

Checks whether a host responds to ICMP when allowed.

curlHTTP evidence

Tests endpoints, headers, status codes, redirects, and TLS.

nslookupDNS check

Confirms whether a name resolves to an address.

digDetailed DNS

Shows DNS records, response sections, TTLs, and resolver behaviour.

ssListening ports

Shows local sockets, listening ports, and related processes.

ncPort testing

Checks whether a TCP port is reachable from a source machine.

tracerouteNetwork path

Shows hops traffic takes toward a destination.

telnetTCP reachability

Older but still useful for quick port connectivity tests.

Hands-on lab

Run the tools in a sensible order

The order matters. Start with name resolution, then reachability, then port testing, then HTTP response. This turns troubleshooting into a repeatable method rather than random command running.

day-7-network-troubleshooting-tools 
nslookup google.com
dig google.com
ping google.com
nc -vz google.com 443
curl -I https://google.com
curl -v https://google.com
ss -tulnp
traceroute google.com

Evidence ladder

Match each symptom to the right command

01 Domain does not work

Use `nslookup` or `dig` to confirm DNS resolution.

02 Host may be unreachable

Use `ping` when ICMP is allowed, then check routes and firewall rules.

03 Port may be blocked

Use `nc -vz host port` from the failing source.

04 Service may not be listening

Use `ss -tulnp` on the server to see listening ports.

05 Application may be failing

Use `curl -I` or `curl -v` to inspect status codes, headers, and TLS details.

Real DevOps scenarios

How these tools help in production-style problems

Ingress

Users see 502 errors

Use `curl -I` to confirm the HTTP status, then check ingress rules, service endpoints, and backend logs. A 502 often means the gateway reached something unhealthy or misconfigured.

Database

The app cannot connect

Use DNS tools for the hostname, `nc` for the database port, and cloud firewall checks for Security Groups, NACLs, and routes.

Server access

SSH is timing out

Check DNS or IP, confirm port 22 reachability, inspect Security Groups, verify routes, and confirm the SSH service is running on the server.

Command patterns

Useful examples to remember

curl -I URL

Show response headers and status code without downloading the full body.

curl -v URL

Show connection, TLS, request, and response details.

nc -vz host 443

Test if a TCP port is reachable.

ss -tulnp

Find local listening ports and the process using each port.

dig domain A

Query A records for a domain.

dig domain CNAME

Check aliases that may point to load balancers.

traceroute host

View the route packets take across the network.

ping host

Check basic reachability, when ICMP is not blocked.

Safe habits

Good troubleshooting is calm and repeatable

Run tests from the same source that is experiencing the problem.

Record the exact command and output before changing anything.

Do not assume ping failure means the server is down; ICMP may be blocked.

Check DNS and port reachability before blaming the application.

Use HTTP status codes to separate network issues from application issues.

Compare failing and working environments to spot drift or missing rules.
