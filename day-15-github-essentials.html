What a professional DevOps repository should communicate

A good repository should quickly answer what the project does, why it exists, what tools are used, how it is run, how it is tested, and what DevOps skills it proves. The goal is not only to store files, but to make the thinking behind the work visible.

Hands-on lab

Create a clean DevOps repository structure

This example creates a simple structure for a DevOps project. You can adapt it for Terraform, Ansible, Kubernetes, Jenkins, Docker, monitoring, or a full CI/CD project. 

mkdir devops-github-essentials
cd devops-github-essentials
git init

mkdir -p .github/workflows docs diagrams scripts screenshots
touch README.md
touch .gitignore
touch docs/architecture.md
touch docs/runbook.md
touch .github/workflows/ci.yml

git status
git add .
git commit -m "Create DevOps repository structure"

README quality

What a strong README should include

Project purpose

Explain what the project does and why it exists.

Tools used

List technologies such as AWS, Docker, Terraform, Kubernetes, Jenkins, or Ansible.

Architecture

Show a diagram or describe the workflow from source code to production.

How to run

Give commands someone can follow to test or understand the project.

How to validate

Show tests, checks, pipeline runs, scans, or health endpoints.

What you learned

Explain trade-offs, improvements, limitations, and next steps.

Example workflow

Add a simple GitHub Actions CI workflow

A repository looks more professional when it proves that checks run automatically. This simple workflow is a starting point. Replace the commands with tests that match your project. 

name: CI

on:
  pull_request:
  push:
    branches:
      - main

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Show repository files
        run: ls -la

      - name: Validate documentation exists
        run: test -f README.md

Security

GitHub security habits to practise

No secrets

Never commit passwords, tokens, private keys, `.env` files, or cloud credentials.

Branch protection

Require reviews and status checks before merging to `main`.

Least privilege

Give workflow tokens only the permissions they need.

Dependabot

Track dependency updates and reduce vulnerable packages.

Secret scanning

Detect accidental exposure early and rotate leaked values quickly.

Clear ownership

Use CODEOWNERS or reviewer rules for important areas.

Release evidence

Use tags and releases to show progress

Tags and releases help explain project progress. They are useful for DevOps portfolios because they show that you understand versioning, change notes, and release communication. 

# Create a version tag
git tag -a v1.0.0 -m "Initial DevOps project release"

# Push the tag to GitHub
git push origin v1.0.0

# Then create a GitHub Release with:
# - what changed
# - screenshots
# - known limitations
# - next improvements

Troubleshooting

Common GitHub portfolio mistakes

No README

The project becomes hard to understand even if the code is good.

Random files

Unstructured uploads look less professional than a clear project layout.

No proof

Add screenshots, workflow runs, commands, diagrams, or validation evidence.

Broken links

Check image paths, relative links, and GitHub Pages URLs.

Secrets committed

Remove and rotate secrets immediately, then improve `.gitignore` and scanning.

No explanation

Explain why the project matters and which DevOps skills it demonstrates.
