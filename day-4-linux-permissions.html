Linux users, groups, and permissions for real DevOps work

Permission problems appear everywhere: deployment scripts that will not execute, services that cannot write logs, containers that cannot read mounted files, and SSH keys rejected because they are too open. Day 4 teaches the access-control habits that make Linux troubleshooting much sharper.

Concept

Linux does not only ask what the file is

Linux also asks who is trying to use it. The current user, group membership, file owner, group owner, and permission bits decide whether an action is allowed or denied.

DevOps value

Permission errors often look like deployment failures

A build may pass, but the deployment may still fail because a script cannot execute, a service cannot write to a directory, or a runtime user cannot read the files it needs.

Permission model

The three access levels

Linux file permissions are usually read as three groups: owner, group, and others. Each group can have read, write, and execute permissions. This simple model explains a large number of real server and CI/CD issues.

u Owner

The user account that owns the file or directory.

g Group

The group assigned to the file or directory.

o Others

Every other user who is not the owner and not in the assigned group.

Bits and numbers

How `r`, `w`, `x`, 755, and 644 connect

Symbolic permissions are easier to read at first, but numeric permissions are common in documentation, scripts, Dockerfiles, CI jobs, and production fixes. The numbers come from adding permission values.

r = 4

Read file contents or list directory contents.

w = 2

Modify a file or change directory contents.

x = 1

Execute a file or enter a directory.

7 = rwx

4 + 2 + 1 gives full access.

5 = r-x

4 + 1 allows read and execute.

4 = r--

Read only.

755scripts and directories 644regular readable files 600private files 700private directories

Hands-on lab

Practise permissions safely in a test folder

The safest way to learn permissions is to create a test file and change its access rules deliberately. This makes `chmod`, `ls -l`, and execution permission easier to understand.

mkdir day-4-permissions-lab
cd day-4-permissions-lab
touch deploy.sh
ls -l deploy.sh
echo "echo Deploy script running" > deploy.sh
./deploy.sh
chmod +x deploy.sh
ls -l deploy.sh
./deploy.sh
chmod 644 deploy.sh
ls -l deploy.sh
chmod 755 deploy.sh
ls -l deploy.sh

Command guide

The commands to practise today

whoami

Show the current logged-in user.

id

Show the user's ID, group ID, and group memberships.

groups

List groups for the current user.

ls -l

Show ownership and permissions for files and folders.

chmod

Change permission bits using symbolic or numeric mode.

chown

Change file or directory owner.

chgrp

Change file or directory group.

sudo

Run a command with elevated privileges when allowed.

Real DevOps failures

Where permission knowledge saves time

Deployment

Script cannot execute

A pipeline downloads or generates a script, but the execute bit is missing. The fix may be as simple as checking `ls -l` and applying `chmod +x script.sh`.

Services

Application cannot write logs

A service may run as a dedicated user and fail because that user does not own the log directory or cannot write to it.

Containers

Mounted files are blocked

Containers can fail when host-mounted files have ownership or permissions that do not match the user running inside the container.

Safe habits

Rules that prevent messy fixes

Check the current user with `whoami` before changing permissions.

Inspect ownership and mode with `ls -l` before using `chmod` or `chown`.

Avoid using `chmod 777` as a quick fix. It often creates unnecessary risk.

Use the minimum permission needed for the file, script, directory, or service.

Protect private keys with restrictive permissions such as `chmod 600`.

Document permission changes so the reason is clear during future troubleshooting.
