How I would modernise a banking platform CI/CD pipeline

By Ebenezer Tetteh · Pipeline to Production

In a banking environment, a CI/CD pipeline is not just a way to deploy code faster. It is a controlled delivery system that should make every change traceable, tested, secure, reviewable, and recoverable before it reaches customers or internal users.

If I were modernising a banking platform CI/CD pipeline, my main goal would be to improve delivery speed without weakening governance. Banking systems often handle sensitive customer data, payment flows, internal financial operations, audit requirements, and high availability expectations. Because of that, the pipeline must support engineering productivity and operational control at the same time.

The starting problem

Many legacy banking release processes become slow because too much work happens manually. Builds may be created differently by different engineers, tests may run inconsistently, deployment instructions may live in documents, and production approvals may happen outside the technical workflow. This creates risk because the team cannot always prove exactly what changed, who approved it, which tests passed, or how quickly the system can recover.

A modern pipeline should reduce those gaps. The delivery process should be repeatable from source code to production, and each stage should produce evidence: test results, scan results, deployment logs, artifact versions, approvals, and monitoring signals.

Modernisation goals

I would design the pipeline around seven goals:

  • Traceability: every deployment should link back to a commit, pull request, build, artifact, approver, and environment.
  • Repeatability: the same pipeline path should build and deploy the application every time.
  • Security: code, dependencies, container images, secrets, and infrastructure changes should be checked before release.
  • Separation of duties: production deployment should require controlled approval, especially for regulated systems.
  • Fast feedback: developers should find out early when code, tests, configuration, or security checks fail.
  • Safe deployment: releases should use health checks, staged environments, and rollback options.
  • Operational visibility: the team should monitor release health using logs, metrics, dashboards, and alerts.

Target pipeline design

At a high level, I would move toward this delivery flow:

pull request
  -> lint and static checks
  -> unit tests
  -> dependency and secret scanning
  -> build container image
  -> image vulnerability scan
  -> Terraform plan
  -> deploy to staging
  -> smoke and integration tests
  -> approval gate
  -> deploy to production
  -> post-deployment monitoring
  -> rollback if needed

This structure keeps production controlled, but it also gives engineers fast feedback before changes reach the release stage. It separates continuous integration from production deployment while still keeping the whole path automated and auditable.

Source control and branch protection

I would start by tightening the source control workflow. The main branch should represent deployable code. Changes should enter through pull requests, with branch protection requiring review and successful automated checks before merge. This gives the team a clear review path and prevents untested code from moving straight into the release branch.

For a banking platform, I would normally recommend short-lived feature branches, pull request reviews, status checks, and protected environments. Long-running branches tend to create painful merge problems and hide risk for too long. Smaller changes are easier to test, review, deploy, and roll back.

Build once and promote the same artifact

One of the most important improvements is to build the application artifact once and promote that same artifact through environments. The team should not rebuild a different image for staging and then rebuild again for production, because that weakens traceability. If the production image was built separately, it becomes harder to prove it is exactly the same code that passed staging tests.

For a containerised banking application, the pipeline should produce a versioned Docker image tagged with the commit SHA and release version. The image should be pushed to a controlled registry, scanned, and then deployed to staging. If staging passes, the same image digest should be promoted to production.

Container image quality

I would use multi-stage Docker builds so the final runtime image contains only what the application needs to run. Docker's guidance explains that multi-stage builds separate build-time tooling from runtime output, which helps reduce image size and attack surface. For a banking workload, that matters because every unnecessary tool, package, or credential inside an image increases operational and security risk. 

FROM node:22-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:stable-alpine AS runtime
COPY --from=build /app/dist /usr/share/nginx/html
EXPOSE 80

The exact base image depends on the application stack, but the principle stays the same: keep the runtime image small, patched, predictable, and free from build tools and secrets.

Security checks inside the pipeline

A banking CI/CD pipeline should include security checks without turning the pipeline into a slow manual queue. OWASP's CI/CD Security Cheat Sheet highlights risks such as weak access control, credential hygiene problems, dependency chain abuse, insecure pipeline configuration, artifact integrity issues, and poor logging visibility. I would address those risks directly in the pipeline design.

The security stage would include:

  • Secret scanning: block committed credentials before they reach the main branch.
  • Dependency scanning: check application packages for known vulnerabilities.
  • Static analysis: catch risky code patterns early.
  • Container scanning: scan the built image before it can be deployed.
  • Infrastructure scanning: check Terraform and Kubernetes configuration for risky settings.
  • Least privilege: give pipeline jobs only the permissions they need.
  • Environment secrets: expose production secrets only to approved production deployment jobs.

The pipeline itself should be treated as a sensitive production system. If an attacker compromises the pipeline, they may be able to alter builds, steal secrets, or deploy malicious code. That is why pipeline permissions, runner security, third-party actions, and deployment credentials need proper control.

Example GitHub Actions workflow

This is a simplified example of how I would structure a GitHub Actions workflow. A real banking environment would add organisation-specific controls, approved runners, stronger secrets management, artifact signing, change records, and integration with release management. 

name: banking-platform-release

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

permissions:
  contents: read
  packages: write
  security-events: write
  id-token: write

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout source
        uses: actions/checkout@v4

      - name: Run lint checks
        run: npm run lint

      - name: Run unit tests
        run: npm test

      - name: Scan for secrets
        run: echo "Run secret scanning tool here"

  build-and-scan:
    needs: validate
    runs-on: ubuntu-latest
    steps:
      - name: Checkout source
        uses: actions/checkout@v4

      - name: Build container image
        run: docker build -t banking-api:${{ github.sha }} .

      - name: Scan image
        run: echo "Run image vulnerability scan here"

      - name: Push image
        run: echo "Push image by immutable digest"

  deploy-staging:
    needs: build-and-scan
    runs-on: ubuntu-latest
    environment: staging
    steps:
      - name: Deploy to staging
        run: kubectl rollout status deployment/banking-api

      - name: Run smoke tests
        run: echo "Run smoke tests against staging"

  deploy-production:
    needs: deploy-staging
    runs-on: ubuntu-latest
    environment: production
    steps:
      - name: Deploy to production
        run: kubectl rollout status deployment/banking-api

      - name: Verify production health
        run: echo "Check metrics, logs, and service health"

GitHub Actions environments can be used for deployment controls such as required reviewers, environment secrets, and deployment protection rules. For production, I would require approval from an authorised reviewer or team before the production job can access production secrets or run deployment steps.

Infrastructure as Code stage

If the banking platform depends on cloud infrastructure, I would manage infrastructure changes through Terraform rather than manual console updates. Terraform should run in a controlled workflow with formatting checks, validation, security scanning, and a plan review before apply. 

terraform fmt -check
terraform validate
terraform plan -out=tfplan
terraform apply tfplan

For team use, Terraform state should be stored remotely rather than only on one engineer's machine. HashiCorp's documentation explains that remote state supports collaboration, and state locking helps prevent concurrent writes that could corrupt infrastructure state. In a banking environment, this is important because infrastructure changes need coordination, auditability, and recovery options.

Kubernetes deployment strategy

For the application deployment layer, I would use Kubernetes Deployments with readiness probes, liveness probes, resource requests, resource limits, and rollout checks. Kubernetes rolling updates allow a Deployment to update pods gradually, which helps reduce downtime when releasing a new version.

The deployment should include:

  • Readiness probes: only send traffic to pods that are ready to serve requests.
  • Liveness probes: restart unhealthy containers when they stop responding correctly.
  • Resource requests and limits: reduce noisy-neighbour problems and improve scheduling.
  • Horizontal Pod Autoscaling: scale workloads based on demand where appropriate.
  • Pod disruption budgets: protect availability during node maintenance or voluntary disruption.
  • Rollback commands: allow fast recovery if a release behaves badly.
kubectl apply -f k8s/
kubectl rollout status deployment/banking-api
kubectl get pods
kubectl logs deployment/banking-api
kubectl rollout undo deployment/banking-api

For higher-risk releases, I would consider blue-green or canary deployment patterns. The right choice depends on the application architecture, database migration risk, traffic routing setup, and monitoring maturity.

Approval gates without blocking engineering flow

Banking delivery often needs approval, but approval should happen at the right point. I would not put a manual approval in front of every small test stage. Instead, the pipeline should run automated checks first. If code quality, security scanning, staging deployment, and smoke tests pass, then the production approval has useful evidence behind it.

A good approval gate answers these questions:

  • What commit and pull request are being released?
  • Which artifact digest is being deployed?
  • Which tests and scans passed?
  • What changed in infrastructure or configuration?
  • What is the rollback plan?
  • Who approved the release?

Secrets and identity

Secrets are one of the highest-risk parts of CI/CD. I would avoid long-lived static credentials wherever possible. A stronger design uses short-lived credentials, workload identity, environment-scoped secrets, and least privilege. Production secrets should only be available to production jobs after the required approval has completed.

OWASP's Secrets Management guidance recommends treating CI/CD tooling as a production environment, monitoring it, and applying least privilege. For banking, that means pipeline credentials should be reviewed, rotated, logged, and limited to the exact systems and actions required.

Artifact integrity and supply chain security

I would also improve software supply chain assurance. The pipeline should make it clear where an artifact came from, how it was built, and whether it was altered after the build. The SLSA specification provides a framework for improving supply chain security through practices such as provenance and stronger build controls.

In practical terms, I would aim to:

  • Use trusted and version-pinned build actions.
  • Generate build provenance where possible.
  • Sign container images or publish attestations.
  • Deploy by immutable image digest rather than mutable tags.
  • Restrict who can change pipeline configuration.
  • Keep deployment evidence for audit and incident review.

Database migration safety

Banking platforms often depend on databases, and database changes can be more dangerous than application changes. I would handle migrations carefully by separating backward-compatible schema changes from application releases where possible. The safest pattern is usually expand, migrate, and contract.

  • Expand: add new tables, columns, or indexes without breaking the current application.
  • Migrate: backfill or move data safely with monitoring and retry behaviour.
  • Contract: remove old fields only after the new application path is stable.

I would avoid pipeline steps that automatically run destructive migrations in production without review. Database migration plans should be visible in the release evidence and should include rollback or forward-fix guidance.

Observability after deployment

A release is not finished when the deployment command succeeds. It is finished when the service is healthy under real conditions. After deployment, the pipeline should verify service health using metrics, logs, traces, and application-level smoke tests.

I would track:

  • HTTP error rate and latency
  • Application exceptions
  • Container restart counts
  • Database connection errors
  • Queue depth or background job failures
  • Business-level signals such as failed transactions or payment errors

For incident response, alerts should link to dashboards and runbooks. If a new deployment causes errors, engineers should not waste time searching for basic commands or ownership details. The runbook should explain how to confirm impact, how to roll back, how to communicate, and how to capture learning after the incident.

Measuring success with DORA metrics

To know whether the modernisation worked, I would measure delivery performance over time. DORA's software delivery metrics focus on throughput and stability, including deployment frequency, change lead time, failed deployment recovery time, change failure rate, and deployment rework rate.

Metric What it shows Why it matters
Deployment frequency How often successful deployments happen Shows whether the team can release in smaller, more regular batches
Change lead time How long a change takes from commit to production Shows whether the delivery path is slow or efficient
Change failure rate How often deployments cause production issues Shows whether speed is being achieved safely
Failed deployment recovery time How quickly the team recovers from failed deployments Shows whether rollback, monitoring, and incident response are effective
Deployment rework rate How much delivery work is unplanned rework Shows whether quality problems are consuming engineering capacity

I would not use these metrics to punish teams. I would use them to find bottlenecks. For example, if lead time is high, the problem might be slow reviews, flaky tests, manual approvals, or environment instability. If change failure rate is high, the problem might be poor test coverage, weak staging parity, risky database changes, or missing observability.

Expected outcome

A successful modernisation should create a delivery process where engineers can release smaller changes with more confidence. The team should be able to answer what changed, what passed, what was deployed, who approved it, and how the system behaved after release.

The practical outcomes I would expect are:

  • Reduced manual deployment effort
  • Better audit evidence for releases
  • Faster feedback for developers
  • Fewer environment-specific deployment surprises
  • Stronger security checks before production
  • Clearer rollback and incident response steps
  • Better visibility into deployment health

What this proves about my DevOps approach

Modernising a banking platform CI/CD pipeline is not only about writing YAML. It requires understanding software delivery, cloud infrastructure, security, governance, Kubernetes operations, observability, and incident response. My approach is to make the delivery path automated where possible, controlled where necessary, and visible at every important step.

For a DevOps engineer, that balance matters. A strong pipeline should help developers move quickly, help security teams trust the release process, help operations teams recover when something fails, and help the business deliver change without losing control.
