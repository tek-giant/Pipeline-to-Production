Monitoring with Kubernetes: from cluster signals to useful action

By Ebenezer Tetteh · Pipeline to Production

Monitoring Kubernetes is not just about installing dashboards. It is about understanding whether applications are healthy, whether the platform has enough capacity, whether deployments are safe, and whether engineers can act quickly when something starts to fail.

Metrics Logs Traces Events Alerts

Kubernetes gives teams a powerful way to run containers, but it also introduces more moving parts: pods, deployments, services, nodes, ingress controllers, persistent volumes, autoscalers, schedulers, and cloud integrations. Without monitoring, it becomes difficult to know whether a problem is caused by the application, resource pressure, networking, storage, scheduling, a bad release, or the cluster itself.

A good Kubernetes monitoring setup should answer simple operational questions quickly: Is the service available? Are pods restarting? Are requests getting slower? Is the cluster running out of CPU or memory? Did the latest deployment increase errors? Are alerts clear enough for someone to take action?

What Kubernetes monitoring should cover

The Kubernetes documentation describes observability as collecting and analysing metrics, logs, and traces to understand the health and internal state of the cluster. In practical DevOps work, I would extend that into a monitoring model that covers workloads, platform components, user-facing symptoms, and incident response.

Workload health

Pod readiness, restarts, deployment rollouts, container resource usage, error rates, and request latency.

Cluster health

Node conditions, CPU, memory, disk pressure, network availability, kubelet status, and control plane signals.

Traffic health

Ingress status codes, upstream errors, request volume, TLS issues, service reachability, and load balancer behaviour.

Release health

Deployment events, rollout status, failed probes, image pull errors, config changes, and rollback signals.

The practical monitoring stack

A common Kubernetes monitoring design uses Prometheus for metrics collection, Grafana for dashboards, Alertmanager or a managed alerting tool for notifications, and a logging stack such as Loki, Elasticsearch, OpenSearch, or a cloud provider log service. Traces can be added with OpenTelemetry, Jaeger, Grafana Tempo, or a managed APM tool.

Pods Exporters Prometheus Grafana Alerts Runbooks

Prometheus works well with Kubernetes because it stores metrics as time series data with labels. Labels are useful because Kubernetes already thinks in labels: namespace, deployment, pod, container, node, service, and environment. That makes it easier to group and filter metrics during troubleshooting.

Layer What to monitor Why it matters
Pod Restarts, status, CPU, memory, logs, readiness, liveness Shows whether an application instance is stable and able to serve traffic
Deployment Available replicas, rollout status, unavailable replicas, events Shows whether releases are progressing safely
Node CPU, memory, disk, network, pressure conditions, kubelet health Shows whether the platform has enough capacity
Ingress Request rate, latency, status codes, upstream errors, TLS Shows how users and external systems experience the service
Application Business errors, dependency latency, queue depth, saturation, custom metrics Shows whether the workload is meeting user and business expectations

Start with the basic commands

Before dashboards, a DevOps engineer should know the command-line checks. Dashboards are excellent for visibility, but commands help when you need immediate evidence during a deployment or incident. 

# Check node resource usage
kubectl top nodes

# Check pod resource usage in a namespace
kubectl top pods -n production

# View pod status, restarts, node placement, and age
kubectl get pods -n production -o wide

# Inspect a deployment rollout
kubectl rollout status deployment/web-api -n production

# Read recent pod logs
kubectl logs deployment/web-api -n production --tail=100

# Check Kubernetes events for scheduling, probe, image, or volume problems
kubectl get events -n production --sort-by=.lastTimestamp

Use probes as monitoring signals

Kubernetes probes are not the whole monitoring system, but they are important health signals. A readiness probe tells Kubernetes whether a pod should receive traffic. A liveness probe tells Kubernetes whether a container should be restarted. A startup probe helps slow-starting applications avoid being killed too early.

Poor probe design can create noise. For example, a liveness probe that fails during a short dependency timeout can restart a healthy application unnecessarily. A readiness probe that does not check a real dependency can send traffic to pods that are technically running but not ready to serve users. 

readinessProbe:
  httpGet:
    path: /ready
    port: 8080
  initialDelaySeconds: 10
  periodSeconds: 10

livenessProbe:
  httpGet:
    path: /health
    port: 8080
  initialDelaySeconds: 30
  periodSeconds: 20

Design dashboards around decisions

A useful dashboard should help someone decide what to do. I would avoid dashboards that only show every available metric. Instead, I would build views around service health, release confidence, capacity, and incident response.

Service health dashboard

Request rate, error rate, latency percentiles, pod readiness, restarts, and dependency health.

Release dashboard

Current version, deployment time, rollout status, error change, latency change, and rollback indicators.

Cluster capacity dashboard

Node CPU, memory, disk pressure, allocatable capacity, pending pods, and autoscaler behaviour.

Alert on symptoms, not every metric

The fastest way to make monitoring useless is to alert on everything. Good alerts should represent user impact, real operational risk, or action that someone can take. If an alert does not require action, it should usually be a dashboard signal or a log query, not a page.

Weak alert Better alert Reason
CPU above 80% CPU saturation causing latency or throttling for 10 minutes High CPU alone may be normal during traffic spikes
One pod restarted Repeated restarts reducing available replicas below target One restart may be harmless; loss of availability is more important
Ingress has one 500 error 5xx rate above threshold for a sustained period Alert on patterns that affect users

Connect monitoring to SLOs

Monitoring becomes more powerful when it is connected to service level objectives. An SLO gives the team a target, such as 99.9% successful requests over 30 days or 95% of requests below 300ms. Instead of arguing about whether a chart looks bad, the team can compare real behaviour against the reliability target. 

# Example PromQL-style questions
rate(http_requests_total{status=~"5.."}[5m])

histogram_quantile(
  0.95,
  rate(http_request_duration_seconds_bucket[5m])
)

sum(rate(container_cpu_usage_seconds_total{namespace="production"}[5m])) by (pod)

Include logs and traces

Metrics tell you that something changed. Logs often explain what happened. Traces show how a request moved across services and where time was spent. Kubernetes monitoring should not treat these as separate worlds. During an incident, engineers should be able to move from an alert to a dashboard, from the dashboard to relevant logs, and from logs to a trace or request ID where available.

The Kubernetes documentation notes that cluster-level logging needs storage and lifecycle outside individual nodes, pods, and containers. That matters because pods are temporary. If a pod is evicted or a node dies, the team still needs access to the evidence.

What I would build for a production team

For a production Kubernetes environment, I would create a minimum monitoring foundation before relying on the platform for critical workloads.

  • Metrics Server for basic CPU and memory visibility used by `kubectl top` and autoscaling workflows
  • Prometheus-compatible metrics collection for workloads, nodes, Kubernetes objects, and ingress controllers
  • Grafana dashboards focused on service health, cluster capacity, release health, and incident response
  • Centralised logs with retention, search, labels, request IDs, and access controls
  • Alerting rules linked to runbooks, ownership, severity, and escalation routes
  • OpenTelemetry or another tracing approach for distributed services where request paths cross multiple components

Common mistakes to avoid

Only monitoring nodes

Healthy nodes do not always mean healthy applications. Workload and user-facing signals matter.

No alert ownership

If nobody owns the alert, it becomes noise. Every important alert should have a team and a runbook.

Too many dashboards

More dashboards do not automatically mean better visibility. Build dashboards around decisions.

No retention plan

Metrics and logs need sensible retention, cost control, and access policies.

My practical conclusion

Monitoring with Kubernetes should make production easier to understand. The goal is not to collect every possible metric. The goal is to help teams detect problems early, understand impact, troubleshoot quickly, recover safely, and improve the platform after incidents.

A strong Kubernetes monitoring setup gives engineers confidence. They know what is running, what changed, what is unhealthy, who is affected, and what action to take next. That is the difference between dashboards that look impressive and monitoring that genuinely supports production.
