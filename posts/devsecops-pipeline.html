DevSecOps

Adding security checks without slowing every deployment

By Ebenezer Tetteh · Pipeline to Production

DevSecOps is not about adding a wall of security tools at the end of delivery. It is about placing the right checks at the right stage, giving developers fast feedback, and making production releases safer without turning every deployment into a slow approval queue.

If I were improving security in a CI/CD pipeline, my goal would be to reduce risk while preserving delivery flow. Security should help the team find problems earlier, fix them with clear ownership, and prove that important controls were applied before production. The pipeline should protect the business, but it should also respect the reality that engineering teams need to ship small changes regularly.

The problem with slow security gates

A common mistake is to treat security as one large checkpoint just before production. By that point, the change has already been designed, coded, reviewed, packaged, and scheduled for release. If a serious problem appears late, the team faces delay, rework, pressure, and sometimes risky exceptions.

A better approach is to shift useful checks earlier while keeping production gates focused on the highest-risk decisions. Developers should receive quick feedback while they are still working on the change. Security teams should get visibility into risk trends. Operations teams should know that deployed artifacts were built, scanned, and approved through a repeatable process.

What I would optimise for

I would design the security checks around five principles:

  • Fast feedback: lightweight checks should run early on pull requests.
  • Risk-based gating: only serious or policy-breaking issues should block release automatically.
  • Clear ownership: every finding should have a responsible team and a practical fix path.
  • Repeatable evidence: the pipeline should record what was scanned, what passed, and what was approved.
  • Least privilege: pipeline jobs, secrets, runners, and deployment identities should use only the access they need.

Target DevSecOps pipeline

The pipeline should layer security checks throughout delivery. This avoids one slow security phase and gives the team several chances to catch issues before production. 

developer workstation
  -> pre-commit secret checks
  -> pull request review
  -> linting and unit tests
  -> SAST and dependency scanning
  -> build container image
  -> image vulnerability scan
  -> generate SBOM and provenance
  -> infrastructure as code scan
  -> deploy to staging
  -> smoke tests and optional DAST
  -> production approval gate
  -> deploy immutable artifact
  -> monitor runtime signals

Not every check needs to block every commit. The pipeline should distinguish between quick developer feedback, release-blocking policy checks, and continuous monitoring that creates follow-up work.

Security checks by stage

Stage Security check Purpose Should it block?
Before commit Secret scanning and formatting Prevent credentials and obvious mistakes from entering Git history Yes for secrets
Pull request SAST, dependency scan, peer review Catch insecure code paths and vulnerable packages before merge Yes for high-confidence critical issues
Build Container scan, SBOM, image signing Prove what was built and detect vulnerable runtime components Yes for critical exploitable issues
Infrastructure IaC policy checks Prevent risky cloud, Kubernetes, and network configuration Yes for policy violations
Staging Smoke tests, DAST where suitable Validate deployed behaviour before production Yes for release-breaking failures
Production Approval gate and runtime monitoring Confirm release evidence and watch real service health Approval blocks; monitoring triggers response

Secret scanning

Secret scanning is one of the first controls I would add because leaked credentials can create immediate risk. Secrets should not be committed into repositories, stored in Docker images, printed in logs, or left in pipeline command history. OWASP's CI/CD and Secrets Management guidance both emphasise strong credential hygiene and least privilege because CI/CD systems often hold powerful access to production resources.

I would use secret checks at multiple points: local pre-commit hooks for developer feedback, pull request checks before merge, and platform-level scanning for repository visibility. If a real secret is detected, the response should include revocation and rotation, not just deleting the line from Git. 

security rule:
  if committed_secret_detected:
    block_merge
    revoke_secret
    rotate_credential
    review_access_logs
    document_incident

Static application security testing

Static application security testing, often called SAST, analyses source code for insecure patterns. GitHub's code scanning documentation describes code scanning as a way to identify security vulnerabilities and coding errors in a repository, with alerts shown where developers can triage and fix them.

I would run SAST on pull requests and on the main branch. The important design decision is how to handle findings. A noisy scanner that blocks every low-confidence issue will slow teams down and encourage bypasses. A better setup blocks high-confidence critical issues, reports medium and low findings for triage, and tracks unresolved findings over time.

Dependency scanning

Modern applications rely on external packages, so vulnerable dependencies are a real delivery risk. GitHub's Dependabot documentation explains that Dependabot alerts help find and fix vulnerable dependencies before they become security risks. For a DevOps pipeline, dependency scanning should be part of the normal engineering rhythm, not an occasional manual exercise.

I would make sure package manifests and lock files are committed, dependency updates are reviewed, and critical dependency vulnerabilities are visible to the team. Where possible, automated pull requests can update vulnerable dependencies, but production impact should still be tested before release. 

dependency policy:
  critical vulnerability with fix available -> block release
  high vulnerability in reachable package -> require review
  medium or low vulnerability -> track with owner and target date

Container image scanning

Container images should be scanned after they are built because the final image may include operating system packages, language dependencies, and runtime components that are not obvious from the source repository alone. Docker's build guidance recommends practices such as multi-stage builds, choosing the right base image, rebuilding images often, excluding unnecessary files, and avoiding unnecessary packages.

I would use a small base image, build with a multi-stage Dockerfile where appropriate, run the application as a non-root user, and scan the final image before it can be promoted. I would also deploy by immutable image digest rather than a mutable tag such as `latest`. 

image controls:
  use minimal base image
  remove build tools from runtime image
  scan final image
  tag with commit SHA
  deploy by image digest
  rebuild when base images receive security updates

Infrastructure as Code security

Infrastructure changes can introduce risk just as easily as application changes. A security group opened to the internet, an overly broad IAM role, an unencrypted storage bucket, or a privileged Kubernetes manifest can create serious exposure. That is why I would scan Terraform, Kubernetes, and cloud configuration as part of the pipeline.

IaC checks should run on pull requests before changes are applied. The pipeline should show the Terraform plan or Kubernetes manifest diff, then apply policy checks against the proposed change. Production infrastructure changes should require approval and leave an audit trail. 

terraform fmt -check
terraform validate
terraform plan -out=tfplan
iac-scan tfplan
manual approval
terraform apply tfplan

Software supply chain controls

DevSecOps also needs to protect the build chain itself. The SLSA specification focuses on improving software supply chain security through stronger build practices and provenance. In practical terms, I would want to know where an artifact came from, what source commit created it, which workflow built it, and whether the artifact was changed after the build.

I would improve supply chain confidence by:

  • Pinning third-party actions and build dependencies where practical
  • Restricting who can edit pipeline configuration
  • Using protected branches and required reviews
  • Generating a Software Bill of Materials for release artifacts
  • Signing images or publishing attestations where the platform supports it
  • Deploying the exact artifact that passed tests and scans

Pipeline identity and least privilege

Pipeline permissions should be explicit. GitHub recommends hardening GitHub Actions by understanding token permissions, protecting secrets, and reducing the risk of untrusted code gaining access to sensitive credentials. I would configure workflow permissions carefully instead of relying on broad defaults. 

permissions:
  contents: read
  packages: write
  security-events: write
  id-token: write

For production deployments, I would prefer short-lived credentials through workload identity or OpenID Connect rather than long-lived cloud keys stored as static secrets. If static secrets are unavoidable, they should be environment-scoped, rotated, and available only to the specific deployment jobs that require them.

Approval gates that are useful

Approval should not be a blind click. A production approval gate should show the evidence needed to make a good decision. That includes the commit, pull request, artifact version, scan results, infrastructure plan, staging test outcome, rollback plan, and deployment window.

I would keep approval close to production, after automated checks have already done their work. That way, the approver is not being asked to compensate for missing automation. They are checking whether a release that has already passed the standard controls is ready for production.

Example GitHub Actions security flow

This simplified workflow shows how checks can be layered. In a real organisation, the tools and policies would be chosen based on the application stack, cloud platform, risk appetite, and compliance requirements. 

name: devsecops-release

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

permissions:
  contents: read
  packages: write
  security-events: write
  id-token: write

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Run tests
        run: npm test

      - name: Run static analysis
        run: echo "Run SAST or CodeQL here"

      - name: Scan dependencies
        run: echo "Run dependency scanner here"

      - name: Check for secrets
        run: echo "Run secret scanning here"

  build:
    needs: validate
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Build image
        run: docker build -t app:${{ github.sha }} .

      - name: Scan image
        run: echo "Run image vulnerability scan here"

      - name: Generate SBOM
        run: echo "Generate SBOM here"

  deploy-staging:
    needs: build
    runs-on: ubuntu-latest
    environment: staging
    steps:
      - name: Deploy staging
        run: echo "Deploy to staging"

      - name: Run smoke tests
        run: echo "Run smoke tests"

  deploy-production:
    needs: deploy-staging
    runs-on: ubuntu-latest
    environment: production
    steps:
      - name: Deploy production
        run: echo "Deploy approved artifact"

How to avoid slowing every deployment

The trick is to separate signal from noise. Not every finding should stop a release, and not every check belongs in the critical path. Some checks should run on pull requests, some should run on scheduled scans, and some should create backlog items rather than blocking deployment.

Practice How it protects speed
Run quick checks first Developers get feedback before waiting for slower scans
Use severity-based gates Only high-risk issues block release automatically
Use baselines Teams can prevent new risk while separately reducing existing backlog
Cache dependencies and scan results Repeated work is reduced where the inputs have not changed
Run slow checks asynchronously Deep scans can inform follow-up without delaying every small change
Give findings clear owners Security work becomes planned engineering work instead of vague noise

Measuring whether it works

A DevSecOps pipeline should improve both security and delivery confidence. I would measure whether the checks are helping the team rather than simply counting how many tools were added.

I would track:

  • Deployment lead time before and after adding controls
  • Number of blocked releases and the reason for each block
  • Mean time to remediate critical vulnerabilities
  • Secret leaks detected before merge versus after merge
  • Container images deployed with critical vulnerabilities
  • False positive rate from scanners
  • Percentage of production deployments with complete release evidence

Common mistakes I would avoid

  • Blocking every deployment for low-confidence scanner warnings
  • Adding tools without defining who owns the findings
  • Using long-lived production credentials in CI/CD jobs
  • Allowing pipeline configuration changes without review
  • Scanning source code but ignoring the final container image
  • Deploying mutable image tags instead of immutable digests
  • Keeping secrets in repositories, images, logs, or build artifacts
  • Treating security as a final manual approval instead of a delivery system

Expected outcome

A good DevSecOps pipeline should help the team release with more confidence, not more confusion. Developers should get security feedback early. Security teams should see evidence and trends. Operations teams should know what was deployed and how it was verified. The business should get a delivery process that supports speed without ignoring production risk.

For me, the key lesson is that DevSecOps is an engineering design problem. The best security checks are not the loudest or the most numerous. They are the checks that catch real risk at the right time, produce useful evidence, and help teams keep improving without breaking delivery flow.
