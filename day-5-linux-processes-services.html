Linux processes and services: understanding what is running

Deploying an application is only the beginning. A DevOps engineer also needs to know what is running, which process owns a port, why a service stopped, how to restart it safely, and where the logs explain the real problem.

Concept

A process is a running program

When a program starts, Linux creates a process and assigns it a process ID, known as a PID. Web servers, databases, background workers, agents, and scripts all run as processes while they are active.

Concept

A service is a managed background application

A service is usually a long-running process controlled by the operating system. On many modern Linux systems, `systemd` manages services through commands such as `systemctl status`, `start`, `stop`, and `restart`.

Runtime model

How Linux keeps applications alive

A production application often depends on more than one running part. There may be a web server, app process, queue worker, database, container runtime, logging agent, and monitoring agent. Day 5 is about learning how to inspect those moving parts.

Key language

The terms to understand first

Process A running instance of a program

Examples include `nginx`, `java`, `python`, `docker`, `sshd`, or a deployment script.

PID Process ID

A unique number Linux uses to track and control a running process.

Daemon A background process

Usually runs continuously without direct user interaction.

Service A managed application

Started, stopped, restarted, enabled, and monitored through the service manager.

systemd Service manager

Controls many Linux services and records service behaviour through the journal.

Port Network listening point

A running process may listen on a port such as 80, 443, 8080, or 3306.

Command guide

The commands to practise today

ps aux

Show running processes with users, CPU, memory, and command details.

top

Watch live CPU, memory, and process activity.

htop

Use a friendlier interactive process viewer when installed.

pgrep

Find process IDs by name.

kill

Send a signal to a process. Use carefully.

systemctl status

Check whether a service is active, failed, enabled, or stopped.

journalctl

Read service and system logs from the systemd journal.

ss -tulnp

Show listening ports and the processes using them.

Troubleshooting map

Use this order when a service is failing

01 Check service state

Run `systemctl status service-name` to see whether the service is active, failed, or stopped.

02 Read recent logs

Use `journalctl -u service-name -n 50` to see the latest error messages.

03 Check the port

Run `ss -tulnp` to confirm whether the expected port is listening.

04 Inspect resources

Use `top` or `htop` to spot CPU, memory, or runaway process problems.

05 Restart with care

Restart only when it is safe, then check status and logs again to confirm recovery.

Real DevOps scenarios

Where process knowledge matters

Deployment

The deploy succeeded, but the app is down

A pipeline can copy files successfully while the service still fails to start. `systemctl status` and `journalctl` show whether the application actually became healthy.

Performance

One process is consuming the server

High CPU or memory can slow the whole machine. `top`, `htop`, and `ps aux` help identify the process responsible before making changes.

Networking

The expected port is not listening

If port 80, 443, or 8080 is closed, users may see downtime even when files are present. `ss -tulnp` connects ports back to processes.

Safe habits

Operate services with discipline

Check status and logs before restarting a service.

Avoid using `kill -9` unless normal shutdown signals fail and the impact is understood.

Confirm the service is listening on the expected port after a restart.

Use `enable` only when the service should start automatically after reboot.

Record the command used, the error seen, and the recovery result.

Treat repeated restarts as a symptom, not the final fix.
