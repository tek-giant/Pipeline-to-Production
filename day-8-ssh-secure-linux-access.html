SSH: secure access to Linux servers like a DevOps engineer

SSH is the secure doorway into Linux servers. In real DevOps work, it is used for administration, troubleshooting, copying files, checking logs, running controlled commands, and accessing cloud instances without relying on passwords.

Start the SSH lab Back to roadmap
Today's focus Key-based secure access

Keys, permissions, `ssh`, `scp`, `rsync`, `~/.ssh/config`, troubleshooting, and safe production habits.

1 Client

Your laptop or workstation starts the encrypted SSH session.

2 Private key

Your private key proves your identity and should never be shared.

3 Network path

Traffic normally reaches the server through TCP port 22.

4 Server

The server checks your public key in `authorized_keys` before allowing access.

Why it matters

SSH is a daily production skill

Even when teams use automation, CI/CD, monitoring, and Infrastructure as Code, engineers still need to understand secure access. When a server is unreachable, a deployment fails, logs need checking, or a cloud instance needs validation, SSH knowledge helps you investigate safely.

Real world

SSH is not just "logging in"

A good DevOps engineer knows how to create keys, protect private keys, connect with the correct user, copy files, use jump hosts, debug permission errors, and avoid risky habits such as password logins or shared keys.

Core concepts

The SSH pieces you need to understand

SSH client

The tool on your machine that starts the secure connection.

SSH server

The remote service, usually `sshd`, that accepts secure access.

Public key

The key you can place on a server to identify allowed users.

Private key

The secret key you protect carefully on your own machine.

Known hosts

A local record that helps detect if a server identity changes.

Authorized keys

The server-side file that lists public keys allowed to connect.

Hands-on lab

Create a secure SSH key and connect to a server

This lab shows the practical flow. Replace the email, username, and server address with your own values when practising. 

# 1. Create a modern SSH key
ssh-keygen -t ed25519 -C "your-email@example.com"

# 2. Check the key files
ls -la ~/.ssh

# 3. Copy the public key to the server
ssh-copy-id ubuntu@your-server-ip

# 4. Connect to the server
ssh ubuntu@your-server-ip

# 5. Confirm who and where you are
whoami
hostname
pwd

File permissions

SSH is strict about permissions for a reason

SSH may reject a key if the files are too open. This protects private keys from being readable by other users on the machine.

chmod 700 ~/.ssh

Only the owner can access the SSH directory.

chmod 600 ~/.ssh/id_ed25519

Only the owner can read and write the private key.

chmod 644 ~/.ssh/id_ed25519.pub

The public key can be readable because it is not secret.

chmod 600 ~/.ssh/authorized_keys

Protect the server-side list of approved public keys.

Better workflow

Use an SSH config file to make access cleaner

Instead of typing long SSH commands every time, you can define friendly host names in `~/.ssh/config`. This is especially useful when managing multiple cloud servers. 

# ~/.ssh/config
Host app-server
  HostName 203.0.113.10
  User ubuntu
  IdentityFile ~/.ssh/id_ed25519
  Port 22

# Connect with the short name
ssh app-server

DevOps use cases

Where SSH appears in real delivery work

Cloud access

Connect to EC2 or Linux VMs to verify services, logs, ports, and configuration.

Deployment checks

Confirm a release by checking service status and application logs after deployment.

File transfer

Use `scp` or `rsync` to copy controlled files between machines.

Incident response

Access a server during an outage to gather evidence before making changes.

Command patterns

Useful SSH commands to practise

ssh user@host

Connect to a remote Linux server.

ssh -i key.pem user@host

Connect with a specific private key file.

ssh -v user@host

Show verbose connection details for troubleshooting.

scp file user@host:/tmp/

Copy a file to a remote server.

rsync -avz src/ user@host:/app/

Synchronise files efficiently over SSH.

systemctl status ssh

Check the SSH service on a Linux server.

Troubleshooting

How to investigate common SSH failures

Permission denied

Check the username, private key, public key placement, and file permissions.

Connection timed out

Check the server IP, firewall rules, security group, route table, VPN, and port 22 access.

Host key warning

Investigate why the server identity changed before removing entries from `known_hosts`.

Too many authentication failures

Specify the correct key with `-i` or use an SSH config entry.

Security habits

How to use SSH safely

Use key-based authentication instead of passwords where possible.

Never share private keys or commit them to GitHub.

Use separate keys for different environments when appropriate.

Restrict SSH access with firewall rules, security groups, or VPN access.

Rotate keys when people leave a team or access is no longer needed.

Use least privilege: avoid logging in as root for normal work.
