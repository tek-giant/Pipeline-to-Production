AWS core services: the building blocks of cloud delivery

Day 22 focuses on the AWS services a DevOps engineer should understand early: compute, storage, networking, identity, databases, monitoring, load balancing, scaling, and container platforms. The goal is to see how the services connect inside a real application, not just memorise names.

Big idea

AWS services become useful when you understand their role in the system.

AWS is large, but DevOps engineers do not need to learn every service at once. Start with the core services that appear in most real environments: compute for running workloads, networking for controlling traffic, IAM for access, storage for files and artifacts, databases for state, monitoring for visibility, and automation for repeatable delivery.

Route 53DNS

Routes users to the public application endpoint.

ALBTraffic entry

Distributes requests to healthy application targets.

EC2 / ECS / EKSCompute

Runs the application workload.

RDSDatabase

Stores relational application data.

CloudWatchOperations

Collects logs, metrics, alarms, and dashboards.

Why this matters

Core services show up in almost every AWS role.

Whether you are building CI/CD, writing Terraform, deploying containers, supporting production, or troubleshooting a live incident, these services are the language of AWS cloud engineering.

What this proves

You can explain infrastructure as a working application path.

A strong explanation follows the request from DNS to load balancer, into private compute, through security boundaries, toward databases and storage, then into logs, metrics, alarms, and recovery processes.

Service groups

The AWS services to understand first

These services are a practical starting point for DevOps. They are not isolated topics; they work together to support secure, scalable, observable, and recoverable applications.

EC2Virtual servers

Run applications, agents, workers, admin tools, and legacy workloads where server control is needed.

S3Object storage

Store artifacts, logs, backups, static assets, reports, and data files durably.

VPCCloud networking

Control subnets, routing, gateways, private access, security boundaries, and traffic paths.

IAMAccess control

Define who or what can access AWS resources and what actions are allowed.

RDSManaged databases

Run relational databases with backups, patching, Multi-AZ options, and monitoring support.

CloudWatchLogs and metrics

Collect operational evidence for dashboards, alerts, troubleshooting, and incident response.

Traffic and scaling

How AWS keeps applications reachable and resilient

Production systems need more than a running server. They need stable entry points, health checks, scaling, and a way to remove unhealthy targets from traffic automatically.

Route 53DNS routing

Maps domain names to application endpoints and supports routing policies.

ALB / NLBLoad balancing

Sends traffic to healthy targets and supports listener rules, TLS, and health checks.

Target groupsHealth checks

Decide which application instances or containers should receive traffic.

Auto ScalingElastic capacity

Adds or removes compute capacity based on demand, schedules, or metrics.

Containers

Where container workflows fit in AWS

Modern DevOps delivery often turns application code into container images. AWS provides services for storing images, running containers, and integrating deployments with CI/CD pipelines.

BuildDocker image

The pipeline builds a repeatable application image.

StoreECR

Amazon Elastic Container Registry stores versioned container images.

RunECS or EKS

Containers run on a managed orchestration platform.

ObserveCloudWatch

Logs and metrics support troubleshooting and scaling decisions.

Production view

What a DevOps engineer checks in an AWS environment

When looking at an AWS workload, think like an operator. Ask whether the system is secure, reachable, observable, recoverable, cost-aware, and easy to rebuild using automation.

AccessAre IAM permissions least privilege?

Prefer roles over long-lived access keys and review production permissions regularly.

NetworkAre private resources protected?

Keep databases and internal workloads away from direct public exposure.

DeployCan the build be repeated?

Use CI/CD, image tags, infrastructure as code, and documented rollback steps.

MonitorCan we see failures quickly?

Use logs, metrics, alarms, dashboards, and runbooks before incidents happen.

RecoverCan the system be restored?

Test backups, Multi-AZ designs, restore procedures, and recovery objectives.

CostAre resources right-sized?

Use tags, budgets, cleanup routines, reserved options, and usage reviews.

Day 22 takeaway

Do not learn AWS as disconnected service names.

Learn AWS by following a real workload: how traffic enters, where code runs, where data lives, how access is controlled, how logs are collected, how scaling happens, and how the team recovers from failure.
