Git branching: safety lanes for DevOps delivery

Branching lets teams make changes without disturbing the main production-ready code. For DevOps engineers, branches protect Terraform, CI/CD pipelines, Kubernetes manifests, Dockerfiles, Ansible playbooks, and application changes while they are being reviewed and tested.

How branches protect the main line

The main branch should represent the trusted version of the project. A feature branch gives you a separate lane to make changes, test them, and request review before the work becomes part of the shared history.

Why branches matter

They reduce delivery risk

A branch gives teams time to test, scan, validate, review, and discuss a change before it affects shared environments. That matters when changing pipelines, infrastructure, security groups, Helm charts, and production runbooks.

DevOps value

Branches make change visible

Branches create a clear path from idea to review to merge. They make it easier to connect commits, pull requests, CI checks, approvals, deployment evidence, and rollback decisions.

Hands-on lab

Create a feature branch and update a DevOps file

This lab simulates a safe pipeline update. Instead of changing `main` directly, create a branch, make the change, review the diff, commit it, and push the branch for review. 

# Start from the latest main branch
git switch main
git pull origin main

# Create a feature branch
git switch -c feature/update-ci-pipeline

# Make a change
mkdir -p docs
echo "Pipeline update notes" > docs/pipeline-change.md

# Review and commit
git status
git diff
git add docs/pipeline-change.md
git commit -m "Document CI pipeline update"

# Push the branch
git push -u origin feature/update-ci-pipeline

Branch types

Common branches in DevOps workflows

feature/*

Used for planned changes such as adding a workflow, module, script, or manifest.

bugfix/*

Used for correcting non-urgent defects discovered during testing or review.

hotfix/*

Used for urgent production fixes that need focused review and fast release.

release/*

Used to stabilise a group of changes before a scheduled release.

experiment/*

Used to test an idea without polluting the main branch history.

docs/*

Used for README, runbook, diagram, or operational documentation changes.

Commands

Branching commands to practise

git branch

Lists local branches and shows the current branch.

git switch -c name

Creates and moves into a new branch.

git switch main

Moves back to the main branch.

git branch -d name

Deletes a local branch after it is no longer needed.

git push -u origin name

Pushes a branch and tracks it on the remote.

git merge name

Brings another branch into the current branch.

git log --oneline --graph

Shows branch history in a visual way.

git fetch --all

Updates your view of remote branches.

Merge thinking

Merge only after the branch is ready

A branch should not be merged just because the code exists. It should be merged when the change is reviewed, tested, understood, and safe enough for the target branch.

Diff reviewed

Someone has checked what actually changed.

CI passed

Tests, linting, builds, or validation checks are green.

Risk understood

The team knows what the change could affect.

Rollback known

There is a clear way to undo or recover if needed.

No secrets

The branch does not contain credentials, keys, or private config.

Approved

The right reviewer or owner has approved the change.

Conflicts

What a merge conflict means

A merge conflict happens when Git cannot safely combine changes because two branches edited the same part of a file. This is not a disaster. It is Git asking a human to decide which version should win. 

# Bring main into your branch before opening a pull request
git switch feature/update-ci-pipeline
git fetch origin
git merge origin/main

# If there is a conflict:
# 1. Open the conflicted file
# 2. Choose the correct content
# 3. Test the result
# 4. Add and commit the resolution
git add .
git commit -m "Resolve merge conflict with main"

Troubleshooting

Common branching problems

Wrong branch

Run `git branch` or `git status` before editing files.

Branch behind main

Fetch and merge or rebase from `origin/main` before review.

Messy commits

Keep commits focused and avoid bundling unrelated work together.

Conflict panic

Open the file, choose the right lines, test, then commit the resolution.

Unpushed branch

Use `git push -u origin branch-name` so others can see it.

Old branch clutter

Delete merged branches locally and remotely when they are no longer needed.
