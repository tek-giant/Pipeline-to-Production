Day 9 of 100

Logs: follow the evidence before changing anything

Logs are the written record of what a system experienced. They help DevOps engineers move from guessing to evidence by showing when a failure started, which component complained, what changed, and whether the issue sits in the application, server, container, network, database, or dependency path.

Start the log lab Back to roadmap
Today's focus Evidence-based log investigation

`tail`, `grep`, `journalctl`, `docker logs`, `kubectl logs`, timestamps, patterns, and incident notes.

01 Alert

A user reports an error, monitoring fires, or a deployment behaves unexpectedly.

02 Timestamp

Find the exact time window. Good log work starts with a time boundary.

03 Pattern

Search for repeated errors, affected endpoints, status codes, pods, or hosts.

04 Cause

Use the evidence to decide whether the fault is app, infrastructure, config, or dependency related.

Why it matters

Logs stop troubleshooting from becoming guesswork

A deployment might say successful while users still see errors. A server might be online while the application fails to connect to a database. Logs show the gap between "it is running" and "it is working".

DevOps mindset

Collect evidence before applying fixes

In production, random fixes can make an incident worse. A calm engineer checks logs, confirms the scope, captures useful output, and then chooses the safest next action.

Log sources

Where to look first

Application logs

Exceptions, failed requests, database errors, queue failures, and business logic problems.

System logs

Linux service failures, authentication events, kernel messages, resource pressure, and daemon errors.

Container logs

Application output from Docker containers and Kubernetes pods.

Web server logs

Nginx or Apache access logs, upstream failures, 4xx and 5xx responses, and request paths.

Cloud logs

Load balancer logs, CloudWatch logs, audit trails, platform events, and managed service errors.

Pipeline logs

Build failures, test output, deployment errors, credentials issues, and artifact publishing problems.

Hands-on lab

Investigate a Linux service using logs

This lab gives a realistic sequence. The aim is not to memorise commands only, but to build the habit of narrowing the problem with evidence. 

# 1. Check whether the service is running
systemctl status nginx

# 2. Read recent logs for the service
journalctl -u nginx --since "30 minutes ago"

# 3. Follow logs in real time
journalctl -u nginx -f

# 4. Search for errors in a file
grep -i "error" /var/log/nginx/error.log

# 5. View the latest lines
tail -n 100 /var/log/nginx/error.log

Command toolkit

Commands every DevOps engineer should practise

tail -f app.log

Follow a log file as new lines are written.

tail -n 200 app.log

Read the most recent 200 lines without opening the whole file.

grep -i "error" app.log

Search for errors without worrying about letter case.

grep -C 3 "timeout" app.log

Show three lines before and after each match for context.

journalctl -xe

View recent system logs with extra explanation.

journalctl -u service

Read logs for one Linux service.

docker logs container

Inspect stdout and stderr from a container.

kubectl logs pod

Read logs from a Kubernetes pod.

Real examples

What different log messages can tell you

ERROR Database connection refused

Check database endpoint, security group, network path, credentials, service status, and recent config changes.

WARN Request timeout after 30 seconds

Check upstream latency, dependency health, resource saturation, retry behaviour, and load balancer timeout settings.

INFO Deployment version changed

Correlate the timestamp with the first user-facing error to see whether the release introduced the issue.

ERROR Permission denied

Check Linux permissions, IAM permissions, Kubernetes service accounts, secrets, mounted volumes, and file ownership.

Container and Kubernetes logs

How logs help when workloads run in containers

In container platforms, logs should usually go to stdout and stderr so Docker, Kubernetes, and logging platforms can collect them. This makes troubleshooting easier across many replicas. 

# Docker examples
docker ps
docker logs --tail 100 web-app
docker logs -f web-app

# Kubernetes examples
kubectl get pods
kubectl logs web-app-7d9f8c6f4b-abc12
kubectl logs deployment/web-app --tail=100
kubectl logs web-app-7d9f8c6f4b-abc12 --previous

Investigation method

A repeatable way to read logs during an incident

1Define the time window

Start with when the alert fired, when the deployment happened, or when users first reported the issue.

2Check the affected component

Look at the app, service, pod, container, server, or load balancer closest to the symptom.

3Search for repeated patterns

Look for error codes, stack traces, failed dependencies, timeouts, permission errors, and repeated request paths.

4Correlate with change

Compare the first error with deployments, config changes, scaling events, infrastructure updates, or dependency outages.

5Record evidence

Copy the key log lines, timestamps, service names, versions, and commands used before making changes.

6Act safely

Rollback, restart, scale, fix config, or escalate based on evidence, impact, and risk.

Good logging habits

Logs should help people solve problems

Include timestamps and service names so events can be correlated.

Use clear log levels such as INFO, WARN, ERROR, and DEBUG.

Do not log passwords, tokens, private keys, or sensitive personal data.

Add request IDs or correlation IDs for tracing user journeys.

Keep errors actionable by logging what failed and enough context to investigate.

Centralise logs when systems have multiple servers, containers, or services.
