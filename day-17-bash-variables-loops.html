Bash variables and loops: make scripts reusable

Variables and loops are what make Bash scripts flexible. Variables let you store values that may change. Loops let you repeat a task across services, files, endpoints, environments, servers, or namespaces without rewriting the same command again and again.

If a value changes, use a variable. If work repeats, use a loop.

Variables

Stop hardcoding everything

Variables are useful for service names, log paths, thresholds, backup folders, environment names, deployment versions, ports, hostnames, and command-line arguments.

Loops

Repeat work without repeating code

Loops help you check multiple services, process several files, validate endpoints, inspect logs, clean directories, and run the same operation across environments.

Hands-on lab

Check multiple services with one loop

This script checks several services using a variable-backed list. It counts failures and returns a useful exit code for humans and CI/CD pipelines. 

#!/usr/bin/env bash
set -euo pipefail

SERVICES=("nginx" "docker" "ssh")
FAILURES=0

for SERVICE in "${SERVICES[@]}"; do
  echo "Checking ${SERVICE}..."

  if systemctl is-active --quiet "${SERVICE}"; then
    echo "OK: ${SERVICE} is running"
  else
    echo "ERROR: ${SERVICE} is not running"
    FAILURES=$((FAILURES + 1))
  fi
done

if [ "${FAILURES}" -gt 0 ]; then
  echo "Completed with ${FAILURES} service failure(s)"
  exit 1
fi

echo "All services are healthy"
exit 0

Variable examples

Values DevOps scripts often store

Service

`SERVICE_NAME="nginx"` keeps service checks flexible.

Threshold

`DISK_THRESHOLD=80` lets teams adjust alerting behaviour.

Path

`LOG_DIR="/var/log/nginx"` avoids repeating paths everywhere.

Environment

`ENVIRONMENT="staging"` helps scripts behave differently per environment.

Version

`APP_VERSION="1.2.0"` supports build, tag, and deploy scripts.

Endpoint

`HEALTH_URL="https://example.com/health"` supports smoke testing.

Endpoint loop

Validate several application endpoints

Endpoint loops are useful after deployments. You can check `/health`, `/ready`, documentation pages, or API routes before confirming that a release is healthy. 

#!/usr/bin/env bash
set -euo pipefail

BASE_URL="${1:-http://localhost}"
ENDPOINTS=("/" "/health" "/ready")

for ENDPOINT in "${ENDPOINTS[@]}"; do
  URL="${BASE_URL}${ENDPOINT}"
  echo "Checking ${URL}"

  STATUS_CODE=$(curl -s -o /dev/null -w "%{http_code}" "${URL}")

  if [ "${STATUS_CODE}" = "200" ]; then
    echo "OK: ${URL} returned 200"
  else
    echo "ERROR: ${URL} returned ${STATUS_CODE}"
    exit 1
  fi
done

File loop

Process multiple log files

File loops are useful for incident investigation. This example searches multiple logs for error patterns and prints a small summary. 

#!/usr/bin/env bash
set -euo pipefail

LOG_FILES=(
  "/var/log/nginx/error.log"
  "/var/log/syslog"
  "/var/log/auth.log"
)

for LOG_FILE in "${LOG_FILES[@]}"; do
  echo "Scanning ${LOG_FILE}"

  if [ -f "${LOG_FILE}" ]; then
    grep -i "error\\|failed\\|denied" "${LOG_FILE}" | tail -n 5 || true
  else
    echo "Skipping missing file: ${LOG_FILE}"
  fi
done

Loop types

Common loop patterns

for

Best for looping through known lists such as services, files, or endpoints.

while

Useful when repeating until a condition changes, such as waiting for a service.

until

Useful for waiting until a command succeeds.

arrays

Useful for keeping lists safe, especially when items may contain spaces.

arguments

Useful for passing environment, threshold, service, or path values into scripts.

exit codes

Useful for telling CI/CD whether the loop succeeded or failed.

CI/CD example

Run loop-based validation before deployment

A pipeline can run a Bash loop to validate required environment variables before deployment continues. 

#!/usr/bin/env bash
set -euo pipefail

REQUIRED_VARS=("APP_NAME" "IMAGE_TAG" "ENVIRONMENT")

for VAR_NAME in "${REQUIRED_VARS[@]}"; do
  if [ -z "${!VAR_NAME:-}" ]; then
    echo "ERROR: ${VAR_NAME} is not set"
    exit 1
  fi

  echo "OK: ${VAR_NAME} is set"
done

echo "Environment validation passed"

Good habits

Safer variables and loops

Quote variables

Use `"${VALUE}"` so spaces and empty values are handled more safely.

Use arrays

Arrays are safer than plain strings for lists of values.

Validate input

Check that required values exist before using them.

Limit scope

Keep variables close to where they are used where possible.

Handle failure

Decide whether one failed item should stop the script or be counted.

Print context

Show which service, file, or endpoint the loop is currently processing.

Troubleshooting

Common variable and loop problems

Unquoted variables

Can break when values contain spaces or unexpected characters.

Empty values

Can cause scripts to check the wrong target or run unsafe commands.

Wrong list format

Plain strings can behave differently from arrays.

Early exit

`set -e` may stop the script before you collect all results.

No context

Logs become hard to read if each loop iteration does not print what it is checking.

Bad exit code

A script may look successful to CI/CD if it does not return failure correctly.
